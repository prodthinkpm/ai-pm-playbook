# 第 14 课：RAG 基础

> 本课目标：理解 RAG（检索增强生成）的核心原理——为什么大模型需要外部知识，怎么把文档切成块、存进向量库、搜索出来、重排序，最后让模型基于你的资料回答。

---

## 1. 先说结论

纯 LLM 有一个致命问题：**它只知道训练时见过的东西。**

如果你问它 2026 年的公司政策、你的私有文档、或者最新的产品价格——它要么说不知道，要么编一个答案（这就是幻觉）。

RAG 的解决思路很简单：

> **先查资料，再回答。**

不是让模型凭记忆回答，而是：
1. 先去你的知识库里找相关文档
2. 把找到的内容塞进 prompt
3. 让模型基于这些内容生成回答

这样模型就不会瞎编了——它是"看着答案抄"，而不是"凭记忆瞎猜"。

| 对比 | 纯 LLM | LLM + RAG |
|------|--------|-----------|
| 信息来源 | 训练数据（可能过时） | 你给的实时资料 |
| 知识更新 | 需要重新训练 | 换文档就行 |
| 幻觉风险 | 高 | 低（但不会消失） |
| 可解释性 | 差（不知道参考了什么） | 好（知道引用了哪段文档） |
| 成本 | 低 | 高（多一次检索） |

> **RAG 是当前企业落地 LLM 最主流的方式**，没有之一。比微调更常用，因为不需要训练，换文档就能更新知识。

## 2. 生活类比

### 类比：开卷考试 vs 闭卷考试

**纯 LLM = 闭卷考试。**

你只能凭记忆回答。如果老师上课讲过某个知识点，你记住了就能答对。如果没讲过、或者记错了——你就瞎编。

**RAG = 开卷考试。**

老师给你一堆参考资料，你可以随时翻书查：

```
学生（用户）问了一个问题
↓
你（系统）去翻书 / 查资料
↓
找到相关段落
↓
抄到答题纸上
↓
交卷（生成回答）
```

开卷考试的好处：
- 不要求你背下所有东西
- 只要资料里有的，你就能找到
- 引用来源，老师能验证

RAG 也一样：
- 模型不需要记住你的业务知识
- 只要知识库里有，就能检索出来
- 可以显示"参考了第 X 段文档"

### 类比：图书馆管理员 + 学者

还有一个经典类比：

- **向量数据库** = 图书馆，所有书都有索引
- **检索模块** = 图书管理员，根据你的问题找到对应的书
- **LLM** = 学者，看了书之后用自己的话回答你

> **图书管理员找错书，学者再厉害也会答错。** 这就是 RAG 的命门——检索质量决定一切。

## 3. RAG 核心流程

RAG 的全称是 **Retrieval-Augmented Generation**（检索增强生成）。

整个流程只有四个步骤：

```
用户问题
  ↓
步骤 1: 检索（Retrieve）
  从知识库中找到相关文档片段
  ↓
步骤 2: 增强（Augment）
  把找到的文档片段拼进 prompt
  ↓
步骤 3: 生成（Generate）
  LLM 基于 prompt + 文档内容生成回答
  ↓
最终答案（带引用）
```

### 具体过程长什么样？

假设你的产品是做**企业客服知识库**。

用户问：

```text
超过 7 天还能退款吗？
```

**步骤 1：检索**

系统把问题转成 embedding，去向量数据库搜索，找到了这三段：

```text
[文档 A] 普通商品 7 天内可申请无理由退款
[文档 B] 超过 7 天需联系客服人工审核
[文档 C] 生鲜类商品不支持退款
```

**步骤 2：增强**

LLM 收到的 prompt 长这样：

```text
请基于以下资料回答问题：

资料 1：普通商品 7 天内可申请无理由退款
资料 2：超过 7 天需联系客服人工审核
资料 3：生鲜类商品不支持退款

问题：超过 7 天还能退款吗？

请用中文回答，并注明参考了哪些资料。
```

**步骤 3：生成**

模型回答：

```text
普通商品超过 7 天需要联系客服人工审核（参考资料 2）。
如果是生鲜商品，则不支持退款（参考资料 3）。
```

### 为什么这个流程有效？

因为模型**不需要记住**退款政策。

它只需要：
1. 会检索（找到相关文档）
2. 会阅读（理解文档内容）
3. 会概括（用自己的话组织答案）

这三件事，现在的 LLM 都做得很好。

> **RAG 的本质：把"记忆"外包给数据库，让模型专注做"理解和表达"。**

## 4. 分块策略（Chunking）

RAG 的第一个工程问题：**知识库里的文档怎么切？**

你不能把整本书塞进 prompt（上下文窗口有限），也不能切得太碎（丢上下文）。

### 为什么需要分块？

假设你的知识库里有一份 100 页的产品手册。

如果不切块：
- 100 页内容远超 LLM 的上下文窗口
- 即使能塞进去，检索成本也极高

如果切得太细（每句话一个块）：
- 丢失上下文（"它"指的是什么？）
- 检索到的是碎片，LLM 看不懂

需要**折中**。

### 三个关键参数

| 参数 | 说明 | 影响 |
|------|------|------|
| **chunk_size**（块大小） | 每段多少 token | 太小丢上下文，太大浪费 token |
| **chunk_overlap**（重叠） | 相邻块重叠多少 token | 避免切断关键句子 |
| **chunking_method**（切法） | 怎么切 | 不同策略适合不同文档 |

### chunk_size：多大的块合适？

经验值：

| 场景 | 推荐 chunk_size | 原因 |
|------|:--------------:|------|
| 客服知识库（FAQ） | 256-512 token | 问答对简短，精准匹配 |
| 产品文档 | 512-1024 token | 段落完整，适中 |
| 学术论文 | 1024-2048 token | 每节内容连贯，不宜切太碎 |
| 代码文档 | 256-512 token | 函数级别即可 |

> **没有万能大小。** 最佳 chunk_size 取决于你的文档类型和查询长度。

### chunk_overlap：为什么需要重叠？

假设你按每 512 token 切块：

```text
[块 1] ... 但是根据公司政策，7天以内...
[块 2] ... 可以申请全额退款。超过...
```

如果"7天以内可以申请全额退款"这句话刚好被切在块 1 和块 2 之间，两个块都不完整。

加入 overlap（比如 128 token），块 1 末尾和块 2 开头会重叠一部分：

```text
[块 1] ... 但是根据公司政策，7天以内可以申请全额退款。
[块 2] 7天以内可以申请全额退款。超过 7 天需人工审核...
```

这样两个块都包含完整的关键句子。

> **推荐初始设置：overlap = chunk_size 的 10-20%。**

### 分块方法

**方法 1：固定长度切块（最基础）**

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=128,
    separators=["\n\n", "\n", "。", "！", "？", " ", ""]
)
chunks = splitter.split_text(your_document)
```

`RecursiveCharacterTextSplitter` 的策略：
1. 先试着按段落（\n\n）切
2. 如果一段太长，按句子（\n）切
3. 如果还太长，按句号（。）切
4. 最后按空格或字符切

这样切出来的块尽量在"自然边界"上，不会从句子中间断开。

**方法 2：语义分块（更智能）**

语义分块不是按固定长度切，而是**按内容变化切**。

当文档话题改变时，才切下一块：

```text
[第 1 段] 退款政策：7 天内可退款...
[第 2 段] 退货流程：登录账号，进入订单...
[第 3 段] 物流政策：包邮条件...
```

语义分块会用 embedding 检测内容变化，在"话题切换"的地方切块。

优点是块更有意义，缺点是计算量大。

| 方法 | 优点 | 缺点 | 适合场景 |
|------|------|------|---------|
| 固定长度+递归 | 简单、快、可预测 | 可能切在句子中间 | 大部分场景（首选） |
| 语义分块 | 块更有意义、上下文完整 | 慢、不可预测块大小 | 长文档、学术文章 |

> **从递归切块开始。** 90% 的场景用递归文本切分器就够了。语义分块是进阶优化。

## 5. Embedding 和向量数据库

第 3 课已经讲了 embedding 的基础。这里重点讲**如何选用**。

### 选择 Embedding 模型

不是所有 embedding 模型都一样。选择时看三个指标：

| 指标 | 说明 | 影响 |
|------|------|------|
| **维度（dimension）** | 每个向量有多少个数字 | 越高越精确但也越贵越慢 |
| **最大输入长度** | 一次能处理多少 token | 越长越能处理长文档 |
| **语言支持** | 是否支持中文 | 中文场景必须测试 |

常用 embedding 模型对比：

| 模型 | 维度 | 最大输入 | 中文表现 | 费用 |
|------|:---:|:--------:|:-------:|:----:|
| text-embedding-3-small (OpenAI) | 1536 | 8192 token | 好 | 低 |
| text-embedding-3-large (OpenAI) | 3072 | 8192 token | 很好 | 中 |
| BAAI/bge-large-zh-v1.5 | 1024 | 512 token | 优秀 | 免费（开源） |
| sentence-transformers/all-MiniLM-L6-v2 | 384 | 256 token | 一般 | 免费（开源） |
| voyage-2 (Voyage AI) | 1024 | 16000 token | 好 | 中 |

> **中文场景强烈推荐 BGE（BAAI 出品）或 OpenAI embedding。** 不要用只训练在英文上的模型来做中文 RAG。

### 向量数据库存什么？

向量数据库里的每一条记录包含三个部分：

```text
{
  "id": "doc-001-chunk-003",      # 唯一 ID
  "vector": [0.12, -0.45, ...],   # embedding 向量（关键！）
  "metadata": {                    # 元数据
    "source": "退款政策.pdf",
    "page": 3,
    "chunk_index": 3,
    "category": "refund"
  },
  "text": "7天内可申请退款..."     # 原始文本（用于展示和 prompt）
}
```

检索时不是按 ID 查，而是按**向量距离**查。

### 向量搜索：ANN 和 HNSW

在向量数据库里搜索，核心问题是：

> 给你一个查询向量，在几百万个向量中找出最接近的 Top-K 个。

**穷举搜索（暴力搜索）**：和每个向量算一遍距离。

- 缺点：100 万个向量 → 100 万次计算 → 太慢

**ANN（Approximate Nearest Neighbor，近似最近邻）**：

- 不找"最精确"的，而是找"足够接近"的
- 速度快 10-100 倍，精度损失很小

**HNSW（Hierarchical Navigable Small World）**：

当前最流行的 ANN 算法。它的思路：

```
想象你在一座大型图书馆里找书
你不需要走遍每个书架
你先看「区域索引」→ 找到「楼层」→ 找到「书架」→ 找到「书」
```

HNSW 给向量建了一个**多层索引**：
- 顶层：粗分（像大洲）
- 中间层：细分（像国家、城市）
- 底层：精确位置（像街道）

搜索时从顶层往下走，每层只检查附近的几个节点，跳过大量不相关的向量。

| 算法 | 速度 | 精度 | 内存占用 | 适合场景 |
|------|:---:|:----:|:-------:|---------|
| 穷举搜索（KNN） | 极慢 | 100% | 低 | 数据量小（<1万） |
| HNSW | 极快 | 99%+ | 高 | 最常用 |
| IVF（倒排文件） | 快 | 95-98% | 中 | 超大向量库 |
| 乘积量化（PQ） | 快 | 90-95% | 极低 | 内存有限 |

> **HNSW 是目前向量数据库事实上的默认算法。** 如果你不知道选什么，选 HNSW。

### 常用向量数据库

| 数据库 | 部署方式 | 适合场景 |
|--------|---------|---------|
| Chroma | 本地嵌入 | 小项目、学习、原型 |
| Milvus | 分布式服务 | 生产环境、海量数据 |
| Qdrant | Docker/云服务 | 生产环境、中等规模 |
| Pinecone | 全托管 SaaS | 不想管运维 |
| pgvector (PostgreSQL) | 作为插件 | 已有 PostgreSQL 的项目 |

> **小项目从 Chroma 或 pgvector 开始。** 大项目用 Milvus 或 Qdrant。

## 6. 检索管道

把以上内容串起来，一个完整的 RAG 检索管道长这样：

```
用户问题
  ↓
步骤 1：把问题转成 embedding
  ↓
步骤 2：在向量数据库中搜索 Top-K（如 Top-20）
  ↓
步骤 3：对搜索结果进行重排序（rerank），选 Top-5
  ↓
步骤 4：根据元数据做过滤（如权限、类别、时间）
  ↓
步骤 5：把最终的 3-5 段文本塞进 prompt
  ↓
LLM 生成回答
```

### 为什么需要这么多步骤？

你可能会想：不能直接搜索 Top-5 就完事了吗？

问题是 **embedding 搜索不够精确。**

举例：

用户问："怎么注销账号？"

向量搜索返回 Top-20 可能包含：
- 第 1 名：注销账号流程（完全匹配） ✅
- 第 3 名：修改密码（语义相近但不相关） ❌
- 第 7 名：账号被盗怎么办（不同主题） ❌
- 第 15 名：会员等级说明（完全不相关） ❌

如果你直接取 Top-5，可能有一半是错的。

**好的策略是：**
1. 多搜一些（Top-20）
2. 重排序（精准排名）
3. 按业务规则过滤（比如只取退款类文档）
4. 最后才交给 LLM

## 7. 什么是重排序器（Reranker）？

这是 RAG 里最关键但常被忽略的组件。

### 为什么 embedding 相似度不够？

Embedding 是把文字压缩成一个向量，这个过程**丢失了精确匹配信息**。

比如：

```text
文档 A：7 天内可退款
文档 B：超过 7 天不可退款
```

它们的 embedding 可能很接近（都是讲退款的），但**意思完全相反**。

Embedding 找"大概相关"的内容很好，但找"精确相关"的内容不够好。

### Reranker 怎么工作？

重排序器（Reranker）**不做压缩**。

它把**查询 + 候选文档**一起放进一个模型，计算它们之间的精确匹配分数：

```text
重排序器(问题, 候选文档) → 精确匹配分数
```

Embedding 搜索就像"看一眼书名"来判断书是否相关。

Reranker 就像"翻开书读几页"来判断是否真的相关。

| 对比 | Embedding 搜索 | Reranker |
|------|--------------|----------|
| 计算方式 | 查询向量 × 文档向量 | 查询 + 文档一起输入模型 |
| 速度 | 极快（百万级/秒） | 慢（只能处理几百个） |
| 精度 | 中等（抓大意） | 高（精确匹配） |
| 使用场景 | 第一轮初筛 | 第二轮精排 |

### 典型组合

```text
Step 1: Embedding 搜索 → Top-100（快筛，从百万到一百）
Step 2: Reranker → Top-5（精排，从一百到五个）
```

这叫**两阶段检索**。Embedding 负责"宽进"，Reranker 负责"严出"。

### 常用 Reranker 模型

| 模型 | 中文表现 | 费用 |
|------|:-------:|:----:|
| BAAI/bge-reranker-v2-m3 | 优秀 | 免费（开源） |
| Cohere Rerank v3 | 好 | 付费（API） |
| Voyage AI rerank-1 | 好 | 付费（API） |
| Jina Reranker v2 | 好 | 付费（API） |

> **建议：RAG 刚起步时可以先不加 reranker，当检索质量不够时加。** 加了 reranker 通常能提升 10-20% 的检索准确率。

## 8. 混合搜索

还有一个常见的问题：**纯语义搜索在某些场景不如关键词搜索。**

比如用户搜：

```text
订单号：ORD-2026-0512-001
```

这是一个精确字符串，embedding 搜索很难匹配"看起来像"的东西。你不需要语义理解，你需要**精确匹配**。

又比如用户在找一篇叫"退款流程"的文章——关键词"退款流程"直接匹配标题比任何语义搜索都准。

### 混合搜索 = 关键词搜索 + 语义搜索

```
用户问题
  ↓
┌──────────────────────┐
│  关键词搜索（BM25）   │   ← 精确匹配
└────────┬─────────────┘
         ↓
┌──────────────────────┐
│  Embedding 语义搜索   │   ← 模糊匹配
└────────┬─────────────┘
         ↓
       合并结果 ← 加权融合
         ↓
     重排序（可选）
         ↓
     最终结果
```

**BM25** 是经典的关键词搜索算法，就是搜索引擎（比如 Elasticsearch）用的那个。它擅长精确匹配关键词。

**Embedding** 擅长语义匹配（同义改写、模糊意图）。

两者结合：

| 场景 | 关键词搜索 | 语义搜索 | 混合搜索 |
|------|:---------:|:--------:|:--------:|
| 搜"订单号：ORD-001" | ✅ 完美 | ❌ 不行 | ✅ 完美 |
| 搜"怎么把钱拿回来" | ❌ 可能找不到 | ✅ 找到"退款" | ✅ 完美 |
| 搜"退款" | ✅ 精确 | ✅ 也能找到 | ✅ 双重保障 |

### 混合搜索的常见做法

```python
# 加权融合（Reciprocal Rank Fusion, RRF）
def rrf(results_keyword, results_semantic, k=60):
    scores = {}
    for rank, doc_id in enumerate(results_keyword):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    for rank, doc_id in enumerate(results_semantic):
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

RRF 的思路很简单：
- 在关键词搜索结果中排名靠前的文档获得一个高分
- 在语义搜索结果中排名靠前的文档也获得一个高分
- 加在一起，综合排名

> **混合搜索是生产环境 RAG 的标配。** 纯语义搜索在精确查询场景会翻车。

## 9. RAG 评估

RAG 系统好不好，不能只靠感觉。需要用量化指标。

### 三个评估维度

| 维度 | 看什么 | 为什么重要 |
|------|--------|-----------|
| **检索质量** | 找没找对文档 | 基础：找都找不对，答案必错 |
| **答案质量** | 回答得好不好 | 找对了也不代表答得好 |
| **延迟** | 用户等多久 | 用户体验：太慢就没人用 |

### 检索质量指标

| 指标 | 定义 | 简单理解 |
|------|------|---------|
| **Recall@K** | K 个结果里有多少个真正相关的 | 有没有漏掉关键文档 |
| **Precision@K** | K 个结果里真正相关的占比 | 找出来的东西干不干净 |
| **MRR** | 第一个正确结果排第几 | 第一个找到的是否就是对的 |
| **NDCG** | 排序顺序好不好 | 越相关的应该排越前 |

举例：

假设知识库里有 100 篇文档，其中 5 篇和用户问题相关。

你搜了 Top-10，返回了 3 篇相关的：

```text
Recall@10 = 3/5 = 60%    # 5 篇里找到了 3 篇（漏了 2 篇）
Precision@10 = 3/10 = 30% # 10 个结果里只有 3 个相关（7 个是噪音）
```

### 答案质量指标

| 指标 | 说明 |
|------|------|
| **Faithfulness（忠实度）** | 答案是否基于检索到的文档，没瞎编 |
| **Relevance（相关性）** | 答案是否回答用户的问题 |
| **Conciseness（简洁度）** | 答案是否简洁，不是废话连篇 |
| **Citation accuracy（引用准确度）** | 引用来源是否正确 |

评估方法：
- **人工评估**：最准但最贵
- **LLM-as-Judge**：让另一个 LLM 打分（如 GPT-4 评估 RAG 答案）
- **自动化指标**：如 BLEU、ROUGE（但不太适合 RAG 场景）

### 延迟

RAG 比纯 LLM 多了一个检索步骤。

```
纯 LLM：用户 → LLM → 回答         ≈ 1-2 秒
RAG：    用户 → 检索 → LLM → 回答  ≈ 2-5 秒
```

延迟分解：

| 步骤 | 耗时 |
|------|:----:|
| Embedding 查询向量 | ~100ms |
| 向量搜索（百万级） | ~50-200ms |
| Reranker | ~50-300ms |
| LLM 生成 | ~1-3 秒 |

> **RAG 通常比纯 LLM 多 1-3 秒。** 在用户体验上需要接受这个折中——准确率换延迟。

## 10. 常见 RAG 失败模式

RAG 不是万能药。知道它会怎么失败，比知道它怎么成功更重要。

### 模式 1：漏掉了上下文（Missing Context）

知识库里有正确答案，但检索没找到。

原因可能是：
- 分块方式不对（关键信息被切断了）
- Embedding 模型不够好（没匹配上语义）
- 查询太简短（"这个怎么弄？" —— 太模糊）

**后果**：LLM 只好瞎编。

### 模式 2：找到了错误的上下文（Wrong Context）

检索返回了不相关的内容，LLM 被误导了。

原因可能是：
- 不同话题的 embedding 过于接近
- Reranker 没加
- Top-K 太大，包含了太多噪音

**后果**：答案看起来合理，但信息是错的。比模式 1 更危险——因为看起来像真的。

### 模式 3：LLM 忽略检索内容（Hallucination）

即使给了正确文档，LLM 还是自己发挥了。

原因可能是：
- Prompt 写得不够硬（没有强调"必须基于资料回答"）
- 模型能力不足（小模型容易被"常识"带跑）
- 上下文太长，模型忽略了关键段落

**后果**：RAG 白做了。

### 模式 4：文档质量差（Garbage In, Garbage Out）

知识库本身就有问题：
- 文档过期
- 文档矛盾（A 说可以退款，B 说不可以）
- 文档混乱（一个文档里混了几个话题）
- 格式问题（PDF 扫描件，OCR 错误多）

**后果**：检索越准，错误越严重。

### 处理策略

| 失败模式 | 对策 |
|---------|------|
| Missing Context | 优化分块、换 embedding 模型、增大 Top-K |
| Wrong Context | 加 reranker、降低 Top-K、加混合搜索 |
| Hallucination | 加固 prompt（"找不到就说找不到"）、换更强模型 |
| 文档质量差 | **先清理数据，再建 RAG** |

> **RAG 最大坑不在模型，在数据。** 很多 RAG 系统的问题追根到底都是文档质量的问题。

## 11. 高级 RAG

以上都是基础 RAG。真实生产环境中还有更多技巧。

### 技巧 1：查询重写（Query Rewriting）

用户的问题不一定适合直接搜索。

```
用户原问："它怎么办？" ← 太模糊，有代词
↓
重写后："如何申请退款？" ← 清晰可搜索
```

查重写的方法：

1. **用 LLM 重写**：把模糊问题转成可直接搜索的查询
2. **查询扩展**：把 "退款" 扩展成 "退款、退货、售后、退钱"
3. **多查询**：生成多个不同角度的查询，分别搜索，合并结果

```python
# 查询重写示例
def rewrite_query(original_query, llm):
    prompt = f"""
    用户的问题是：「{original_query}」
    请把这个问题改写成更适合搜索知识库的形式。
    如果问题有代词（它、这个、那个），请补全。
    只输出改写后的问题，不要解释。
    """
    return llm.generate(prompt)
```

### 技巧 2：多跳检索（Multi-hop Retrieval）

有时一个问题需要**多次检索**才能回答。

```
用户问："去年退款最多的那个产品，今年的销量是多少？"
```

这需要两步：
1. 先查 "去年退款最多的产品是什么" → 得到产品名 "X"
2. 再查 "产品 X 今年的销量" → 得到最终答案

你不能在一个查询里同时问两件事。embedding 会混乱。

多跳检索的做法：

```text
Round 1: 搜索"去年退款最多" → 找到产品 X
         把 X 放进上下文
Round 2: 搜索"产品 X 今年销量" → 找到销量数据
         拼接成最终答案
```

### 技巧 3：迭代检索（Iterative Retrieval）

不是一次搜完，而是**边回答边搜**。

LLM 在生成过程中发现自己缺少某段信息，可以主动触发下一次检索。

```
Round 1: 用户问"介绍一下我们的客服体系"
         检索 → 找到"客服分为一线和二线"
         LLM 生成："我们有..."
         ↓
         LLM 意识到需要一线客服的具体流程
Round 2: 检索"一线客服工作流程"
         找到相关文档
         LLM 继续生成
```

### 技巧 4：句子窗口检索（Sentence Window Retrieval）

搜的时候找小段（精确匹配），给 LLM 的时候给大段（上下文完整）。

```
搜索用：每 1-2 句话一个 embedding 块   ← 精确
给 LLM：命中块前后各扩展 5 句话         ← 上下文完整
```

这样既保证检索精准，又保证上下文不丢失。

### 技巧 5：分层检索（Hierarchical Retrieval）

对超长文档，建两层索引：

```
顶层：章节摘要（几百个 embedding）
底层：段落原文（几千个 embedding）

搜索时：
1. 先搜顶层 → 找到相关章节
2. 再在该章节内搜底层 → 找到精确段落
```

类似先找对书，再翻到具体页码。

## 12. 本课总结

- **RAG = 先查资料，再回答。** 把"记忆"外包给数据库，模型专注理解和表达
- **核心流程**：用户问题 → 检索 → 增强（拼进 prompt） → 生成
- **分块策略**：递归切块（首选），chunk_size 512、overlap 10-20%
- **Embedding 选择**：中文场景推荐 BGE 或 OpenAI
- **向量数据库**：存向量 + 元数据 + 原文，用 HNSW 算法做 ANN 搜索
- **检索管道**：嵌入查询 → 向量搜索（Top-20） → Reranker（Top-5） → 过滤 → LLM
- **Reranker**：把查询和文档一起算精确匹配，比纯 embedding 更准
- **混合搜索** = 关键词（BM25）+ 语义（embedding），生产环境标配
- **RAG 评估**：检索质量（Recall/Precision）、答案质量（Faithfulness）、延迟
- **常见失败**：漏了上下文、找了错误的文档、LLM 自己发挥、文档质量差
- **高级技巧**：查询重写、多跳检索、迭代检索、句子窗口、分层检索

## 13. 心智模型

> **RAG = 开卷考试。**

- **知识库** = 参考书
- **Chunking** = 给书贴便利贴标签
- **Embedding** = 目录索引（根据意思找）
- **向量数据库** = 书架，按索引快速拿书
- **Reranker** = 仔细翻一遍，确定真的有用
- **LLM** = 答题的学生（翻到哪页答哪页）
- **Hybrid search** = 既有目录搜索，也有标签搜索

**两个关键数字记心中：**
1. **检索质量决定 RAG 上限**——LLM 再强，找错了也没用
2. **先清理数据，再建 RAG**——垃圾进，垃圾出

## 14. 初学者常见错误

### 错误 1：不分块，直接塞整篇文档

❌ "我把 100 页 PDF 整个放进去不行吗？"

✅ 上下文窗口有限，必须分块。先切到 512-1024 token 一块。

### 错误 2：Top-K 设太大或太小

❌ Top-1：只取一个结果，漏掉关键信息
❌ Top-50：太多噪音，LLM 都不知道看哪个

✅ 先搜 Top-20，rerank 后取 Top-5。

### 错误 3：不加 Reranker

❌ "向量搜索的结果直接给 LLM"

✅ 纯 embedding 精度不够，两阶段（搜索 + rerank）效果好很多。

### 错误 4：不评估就上线

❌ "感觉回答挺好的"

✅ 没有量化指标，你不知道 100 次里成功了 90 次还是 50 次。

### 错误 5：把 RAG 当搜索用

❌ 用户问"退款政策"，RAG 直接回答"根据资料，退款政策是..."

✅ 有时候用户就是想看原文，RAG 做摘要可能丢细节。考虑"搜索模式" vs "问答模式"。

### 错误 6：忽略权限

❌ 员工 A 问同事的薪资，RAG 从 HR 文档里搜到了并回答

✅ 企业 RAG 必须做权限过滤。元数据里存权限标签，检索后按权限过滤。

## 16. 小项目

**目标**：搭建一个完整的最小 RAG 系统。

**主题**：你公司内部的"请假政策"知识库。

**步骤**：

### Step 1：准备 5 条知识

```text
1. 年假：工作满一年后每年 5 天，需提前 3 天申请
2. 病假：需提供医院证明，1 天内可不提供证明
3. 事假：无薪，需提前 1 天申请
4. 婚假：结婚登记后 6 个月内有效，共 3 天
5. 产假：女性员工 98 天，男性员工陪产假 7 天
```

### Step 2：搭建 RAG 管道

# 1. 分块（每块就是一条知识）
chunks = knowledge_texts  # 因为每条很短，不用再切

# 2. 生成 embedding

# 3. 存入向量数据库
# 用 Chroma / pgvector 等

# 4. 检索
def search(query, top_k=3):
    query_vec = embed(query)
