第 16 课：推理优化与模型部署 ​

本课目标：理解 LLM 推理的核心机制，学会如何让模型跑得更快、更省、更稳定——从 KV cache 到 PagedAttention，从单卡推理到生产级部署框架。

1. 先说结论 ​

训练和推理是 LLM 的两种模式：

  • 训练 = 让模型学习知识（一次性的，很贵）
  • 推理 = 模型用学到的知识回答问题（反复的，所以必须快）

本课讲的全是推理优化。训练你跑一次就完了，但推理是每天百万次调用。省 1 毫秒，一年就是几千小时的算力。

概念一句话
推理（Inference）模型用训练好的参数生成回答
KV cache缓存注意力中间结果，避免重复计算
Flash Attention更快的注意力算法，省显存、提速度
投机解码小模型草稿 + 大模型校验，加速生成
批量推理一次处理多个请求，提高吞吐量
Continuous batching动态调度请求，不浪费计算资源
PagedAttentionvLLM 的内存管理技术，像操作系统的虚拟内存
量化推理降低模型精度，换速度

学好这课，你就能从"能跑"进化到"跑得快、跑得稳"。

2. 生活类比 ​

类比 1：快餐店出餐 ​

你开了一家快餐店，有一个大厨（大模型）。

训练 = 大厨学做菜，花大量时间和学费。

推理 = 客人点单，大厨现场做菜。你关心：

  • 出餐速度（Latency）：下单到拿到菜多久？
  • 翻台率（Throughput）：一小时服务多少客人？

KV cache = 大厨把常用配菜提前切好放冰箱。同一道菜来了直接拿。

批量推理 = 同时做 10 份番茄炒蛋：一次切 10 份番茄，一次炒好。

Continuous batching = 不等前一批做完，新单随时插进锅里。

类比 2：快递站 ​

第一个包裹：翻仓库、拿纸箱、装填、封口贴单——慢。

第二个同类包裹：直接复制粘贴流程——快多了。

KV cache 就是这个"已经翻好的货"。

3. 什么是推理？ ​

推理 vs 训练 ​

维度训练推理
目标让模型学习让模型回答
计算前向 + 反向传播只有前向传播
资源极贵（A100 几百小时）贵但可控（每次几毛钱）
需要保存优化器状态 + 梯度只需模型权重
用户感知无（后台跑）直接（响应时间）

推理的两个阶段 ​

Prefill（预填充）——处理输入：一次性把整个输入跑完，计算所有 token 之间的注意力。

Decode（解码）——逐个生成：每步只生成一个 token，但要走完整个前向传播。

Decode 阶段占了推理 80% 以上的时间。优化推理 = 优化 decode。

4. KV Cache——"记忆"就是速度 ​

问题：重复计算 ​

假设用户输入 100 个 token，要生成 100 个。

每生成一个 token，都要重新算前面所有 token 的注意力——大量重复计算。

第 1 步：算 token 1~100 → 生成 token 101
第 2 步：算 token 1~101 → 生成 token 102  ← 又算了一遍 1~100！
第 3 步：算 token 1~102 → 生成 token 103  ← 又算了一遍 1~101！
...

解决方案 ​

注意力计算中的 K（Key）和 V（Value）矩阵只依赖前面的 token，不依赖新生成的 token。

所以缓存它们。

场景无 KV cache有 KV cache
计算复杂度O(n²) 每步O(n) 每步
实际加速—10~50 倍

KV cache 的成本——显存换速度 ​

7B 模型，2048 token 上下文
→ 每 token 需要 2 (K+V) × 2 字节 (FP16) × 32 层 × 4096 hidden = ~0.5 MB
→ 2048 tokens × 0.5 MB = ~1 GB 显存
模型4K 上下文32K 上下文
7B~2 GB~16 GB
13B~4 GB~32 GB
70B~20 GB~160 GB

KV cache 是 LLM 推理中最大的显存消耗来源之一。 PagedAttention 就是来解决这个问题的。

5. Flash Attention——更快的注意力算法 ​

痛点 ​

标准注意力需要把 K/V 矩阵在 SRAM 和 HBM（显存）之间反复搬运。

python
# 标准 Attention（3 次 HBM 搬运）
HBM → SRAM（加载 Q/K/V）→ 计算 S → HBM（存 S）
HBM → SRAM（加载 S）→ 计算 softmax → HBM（存 P）
HBM → SRAM（加载 P, V）→ 计算 O → HBM（存 O）

数据搬运比计算本身还慢。 这是"内存带宽瓶颈"。

Flash Attention 的做法 ​

把计算分解成小块（tiles），每个小块在 SRAM 一次算完再写回。

维度标准 AttentionFlash Attention
HBM 访问次数多次1~2 次
推理速度基准2~4 倍
显存占用高低
精度—完全无损

Flash Attention 数学上完全等价，只是计算顺序不同。 目前所有主流推理框架的标配。

6. 投机解码——小模型打工，大模型审核 ​

标准自回归生成每步只能生成 1 个 token，不能并行。

投机解码的做法：

1. 小模型（草稿模型）快速生成 5 个候选 token
2. 大模型（目标模型）一次校验全部 5 个
3. 完全一致 → 一次出 5 个 token！
4. 不一致 → 从第一个错误 token 回退重来
场景加速比条件
草稿模型准确率高3~5 倍草稿和目标模型任务相关
准去率低1~1.5 倍退化成标准解码

投机解码不改变输出质量。 大模型最终校验确保和标准解码完全一致——这是"无损加速"。

7. 批量推理 ​

GPU 是大规模并行计算器。适合一次处理大量数据。

python
# 单条处理（慢）
for prompt in prompts:
    result = model.generate(prompt)

# 批量处理（快）
results = model.generate(prompts, batch_size=8)
单条：GPU 算力利用率 50%，耗时 100ms
批量 8 条：GPU 利用率 95%，耗时 200ms（平均每条 25ms）

延迟 vs 吞吐量 ​

场景优先说明
在线聊天延迟每增加 100ms 用户流失
离线批量处理吞吐量一夜处理几百万条
实时翻译延迟需即时反馈
数据标注吞吐量不急于一时

你永远不能同时优化延迟和吞吐量。 批量大 → 延迟高但吞吐高；批量小 → 延迟低但吞吐低。

8. GPU 基础 ​

三个关键概念 ​

概念类比说明
VRAM（显存）工作台大小模型 + KV cache + 中间结果
算力厨师切菜速度GPU 每秒做矩阵乘法的能力
内存带宽材料传送带速度显存到计算核心的搬运速度

为什么内存带宽最重要？ ​

LLM 推理是带宽瓶颈，不是算力瓶颈。

推理过程：
1. 从显存读取模型权重（大量数据）← 瓶颈
2. 送到计算核心做矩阵乘法（计算量不大）
3. 写回显存 ← 瓶颈

常见 GPU ​

GPUVRAM带宽适合
RTX 309024 GB936 GB/s消费级推理
RTX 409024 GB1,008 GB/s消费级推理
A100-80G80 GB2,039 GB/s企业级
H10080 GB3,350 GB/s顶级

推理时，内存带宽比算力更重要。 A100 比 4090 算力高 2 倍，但显存大 3 倍——这才是它能跑大模型的原因。

推理总显存 = 模型权重 + KV cache + 激活值 + 预留开销

你的 GPU能跑什么

显存至少是模型权重 × 1.2。 多出 20% 给 KV cache 和激活值。

12. Continuous Batching——动态批处理 ​

传统批处理的问题 ​

凑齐一批再处理。GPU 在等，显存空转。

请求 A 到达  ░░░░░░░░░░ 等凑齐
请求 B 到达  ░░░░░░░░░░ 等
请求 C 到达  ░░░░░░░░░░ 等
请求 D 到达  ░░░░░░░░░░ 等
开始处理     ████████████████████
            ↑ GPU 利用率 50~70%

Continuous Batching ​

随时到达，随时加入计算。

请求 A 到达  ██████░░░░ 生成中
请求 B 到达  ██████████ 加入
请求 C 到达  ██████████████ 加入
请求 D 完成  ████████████████████ 完成
请求 E 到达  ██████████████████████████ 加入
            ↑ GPU 利用率 95%+
指标传统批处理Continuous Batching
GPU 利用率50~70%95%+
吞度量提升基准2~4 倍

13. PagedAttention——vLLM 的秘密武器 ​

问题：KV cache 内存碎片 ​

传统做法：为每个请求预分配最大可能长度的内存空间。

python
max_length = 2048  # 不管你实际生成长度多短
kv_cache_per_request = alloc(max_length)
                     # 实际只用了 200，浪费 90%

结果：KV cache 利用率只有 20~40%。

解决方案：分页 ​

和操作系统的虚拟内存一模一样。不要求连续内存，用页面表管理。

传统（连续内存）：
| A: 200 tokens | B: 150 tokens | 空着 1700 个位置 |
└───── 利用率 20% ────┘

PagedAttention（分页，不连续）：
页 1: [A]  页 2: [A]  页 3: [B]  页 4: [A]
页 5: [B]  页 6: [A]  页 7: [ ]  页 8: [ ]
               ↑ 利用率 ~90%

效果 ​

维度传统管理PagedAttention
KV cache 利用率20~40%~90%
支持更大 batch受限2~4 倍
内存共享（同 prompt）❌✅ 共享前缀页面

内存共享 ​

100 个用户同时问"帮我写辞职信"——传统做法存 100 份 KV cache。

PagedAttention：共享相同前缀的页面，只在生成差异部分时创建新页面。

传统：100 × 512 页面 = 51200 页面
PagedAttention：512 (共享前缀) + 100 × 50 (差异) = 5512 页面 → 省 90%！

PagedAttention 让 vLLM 在高并发场景下比其他框架快 2~4 倍。

14. 完整优化路径 ​

一个模型从"能跑"到"跑得快"的路径：

阶段 0：裸跑 7B FP16，batch=1
→ 延迟 500ms/token，显存 16 GB

阶段 1：KV cache + Flash Attention（纯算法优化，零成本）
→ 延迟 50ms/token，显存 14 GB

阶段 2：量化（INT4）
→ 延迟 30ms/token，显存 6 GB

阶段 3：投机解码
→ 延迟 10ms/token，显存 8 GB（含草稿模型）

阶段 4：部署到 vLLM（Continuous batching + PagedAttention）
→ 吞吐量提升 3~5 倍，延迟稳定

组合使用，推理速度提升 50 倍，成本降低 90%。
