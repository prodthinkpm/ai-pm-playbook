第 18 课：评估、成本和产品落地 ​

本课目标：学会如何评估模型质量、计算成本、衡量速度——然后回答那个最核心的问题：这个 AI 功能到底能不能上线？

1. 先说结论 ​

你花 18 课学完了 LLM 的原理、微调、RAG、Agent、部署。现在到了最关键的一步：判断你的 AI 功能值不值得做。

很多 AI 产品失败不是因为技术不行，而是因为没有回答这几个问题：

  • 模型效果够好吗？怎么衡量？
  • 一次调用多少钱？用户用 100 次多少钱？
  • 响应速度用户能接受吗？
  • 幻觉和安全问题控制住了吗？
  • 这个功能真的需要 AI 吗？

本课就是教你怎么回答这些问题。

维度核心指标一句话
质量准确率 / 有用率回答对不对、好不好用
速度TPS / TTFT生成快不快、首字快不快
成本成本/次 / 成本/K token用一次多少钱
安全幻觉率 / 拒绝率安不安全、有没有瞎编

上线的标准 = 质量过得去 + 用户等得起 + 公司付得起 + 安全守得住。

2. 生活类比 ​

类比 1：招聘面试官 ​

你招一个客服主管（大模型），你不可能不面试就直接让他上岗吧？

评估模型 = 面试候选人。

  • MMLU（学术笔试）：考他的知识范围——数学、历史、法律常识
  • HumanEval（编程测试）：考他会不会写代码
  • GSM8K（应用题）：考他数学推理能力
  • Chatbot Arena（盲评）：让多个面试官分别聊，匿名打分
  • 你的业务测试（电话模拟）：用 50 个真实的客户场景测他

学术成绩好不一定业务能力强。最终看你的业务场景测出来的结果。

类比 2：开餐厅 ​

你准备开一家 AI 餐厅。

问题餐厅类比AI 产品
菜好不好吃？试吃员打分LLM-as-Judge
出餐快不快？计时器测速度TPS / TTFT
成本多高？算食材成本成本/K token
能开多少桌？算翻台率并发 / Throughput
安不安全？食品安全检查幻觉检测 + 安全过滤

只关心菜好不好吃，不看成本和速度——餐厅必亏。 只关心成本和速度，不管好不好吃——没人来吃。

3.4 GSM8K——数学推理 ​

小学数学应用题。测的是推理能力，不是数学难度。

问题：小明有 12 个苹果，给了小红 1/3，还剩几个？

很多模型知识丰富但推理差。GSM8K 低 = 逻辑能力有缺陷。

3.5 HELM——更全面的评估 ​

Stanford 的 HELM 框架不只看准确率，还看：

  • 校准度：模型说自己 90% 确定时，是不是真的 90% 对？
  • 公平性：对性别、种族等是否偏见？
  • 鲁棒性：输入稍微改一下，答案还一样吗？
  • 效率：速度和成本

3.7 你应该关注哪些基准？ ​

标准做法：看公开基准 + 跑自己的数据。 只看公开基准就像只看考试成绩不看实际工作能力。

4. 人工评估——最可靠但也最贵 ​

4.1 为什么需要人工评估？ ​

基准测试只能告诉你"模型在各种考试中的表现"，不能告诉你"模型在你的产品中好不好用"。

人工评估是"黄金标准"。

4.2 怎么做人工评估？ ​

步骤 1：准备测试用例

50~100 条真实用户场景。不编造，用真实数据。

python
test_cases = [
    {
        "input": "我的订单昨天到了，但少了一件商品",
        "expected": "表示歉意 + 确认订单号 + 安排补发",
        "difficulty": "easy",
        "scenario": "售后"
    },
    {
        "input": "你们的会员卡和信用卡有什么区别？我想知道哪个更划算",
        "expected": "对比两者差异 + 推荐方案",
        "difficulty": "medium",
        "scenario": "销售"
    },
    {
        "input": "我的情况很特殊，（500字长文描述复杂纠纷）",
        "expected": "理解诉求 + 给出可行方案",
        "difficulty": "hard",
        "scenario": "投诉"
    }
]

步骤 2：设计评分标准

维度5 分3 分1 分
准确性完全正确部分正确错误/幻觉
有帮助解决用户问题有点帮助没用
语气自然友好还行机械/生硬
安全无风险需谨慎有风险内容

步骤 3：找 3~5 个评估员

每个 case 至少 2 个人独立打分，取平均。

Case评估员 A评估员 B平均
售后 1454.5
销售 2322.5
投诉 3444.0

步骤 4：算一致性

评估员之间分歧大 → 说明评分标准不清晰，需要重新校准。

4.3 人工评估的成本 ​

维度估算
100 个 case，每个 1 分钟~2 小时
3 个评估员~6 小时
每人时薪 50 元300 元/次评估
每周评估一次1200 元/月

人工评估不贵但你做不了很多次。 所以需要自动化评估来替代。

5.1 评估集 vs 训练集 ​

维度训练集评估集

5.2 一个好的评估集长什么样？ ​

50~100 条，覆盖所有业务场景。

完整评估集（80 条）：
├── 常见场景（40 条，50%）
│   ├── 售后问题 × 10
│   ├── 产品咨询 × 10
│   ├── 账户问题 × 10
│   └── 使用方法 × 10
├── 边缘场景（20 条，25%）
│   ├── 超长输入 × 5
│   ├── 多语言混杂 × 5
│   ├── 情绪激烈 × 5
│   └── 同音字/错别字 × 5
└── 困难场景（20 条，25%）
    ├── 逻辑陷阱 × 5
    ├── 需要多步推理 × 5
    ├── 模糊查询 × 5
    └── 需要拒绝回答 × 5

5.3 评估集维护 ​

频率做什么
每天记录用户反馈的 bad case
每周把 bad case 加入评估集
每月重新评估所有模型版本
每季度重新审查评估集，淘汰过时的

评估集是活的。 产品变了、用户变了、模型变了——评估集也要变。

6. 自动评估——LLM 作为裁判 ​

6.1 为什么需要？ ​

人工评估每次几百块还行，但如果你每天要测 10 个模型版本呢？需要自动化。

LLM-as-Judge（用 LLM 打分）： 让一个强大的 LLM（GPT-4、Claude）给另一个模型的输出打分。

6.2 怎么做？ ​

python
import openai

def llm_judge(question, model_answer, reference_answer):
    """用 GPT-4 给模型回答打分（1~5 分）"""
    
    judge_prompt = f"""
你是一个 AI 评测专家。请根据以下标准给模型回答打分：

问题：{question}

参考答案（标准答案）：{reference_answer}

模型回答：{model_answer}

评分标准：
5 分：完全正确，清晰有用，无幻觉
4 分：正确但不够精确
3 分：部分正确，有遗漏
2 分：有错误信息
1 分：完全错误或拒绝回答

请输出：
分数：[1-5]
理由：[简要说明]
"""

    response = openai.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": judge_prompt}]
    )
    
    return response.choices[0].message.content

6.3 LLM-as-Judge 的可靠性 ​

维度可靠性说明
事实性问题⭐⭐⭐⭐⭐"巴黎是法国首都吗"——很准
开放性回答⭐⭐⭐"写一首诗"——主观
代码评估⭐⭐⭐⭐编译/运行检查最可靠
创意写作⭐⭐偏好差异大

6.4 最佳实践 ​

python
# 用多个 LLM 投票提高可靠性
judges = ["gpt-4", "claude-3-sonnet", "gemini-pro"]
scores = []

for judge in judges:
    score = llm_judge(question, answer, reference, judge_model=judge)
    scores.append(score)

# 取中位数，抛掉极端值
final_score = median(scores)
方法和人工一致性成本
单个 LLM 打分60~80%低
3 个 LLM 投票75~90%中
LLM + 人工抽检85~95%适中
纯人工100%（但慢）高

推荐组合：80% 自动 + 20% 人工抽检。 既省钱又不放过 bad case。

7. 成本分析——用一次多少钱？ ​

7.1 API 定价结构 ​

主流 API 按输入 token + 输出 token 分别计价。

模型输入（/M token）输出（/M token）
GPT-4o$2.50$10.00
GPT-4o-mini$0.15$0.60
Claude 3.5 Sonnet$3.00$15.00
Gemini 1.5 Pro$1.25$5.00

输出比输入贵 3~4 倍。 因为输出是逐 token 生成的，计算量大。

7.3 降成本的常用方法 ​

方法效果副作用
用小模型省 80%质量可能下降
用更短 prompt省 20~50%需要精心设计
缓存重复问题省 30~70%需要缓存系统
批量处理省 30%延迟增加
本地部署省 50~90%有运维成本
量化模型省 50%质量略降

7.4 成本管理心智模型 ​

成本 = 单次成本 × 次数。 单次便宜但量大一样贵。

模式成本控制重点
低频（<1000 次/月）不用管，用最好的模型
中频（1万~10万次/月）用小模型 + prompt 优化
高频（>100万次/月）考虑本地部署 + 缓存

AI 产品的成本核算是产品经理的必修课。 用错了模型，一年亏几十万。

8. 速度评估 ​

8.1 两个核心指标 ​

指标全称定义用户体验
TTFTTime To First Token从发出请求到收到第一个 token感觉"有没有响应"
TPSTokens Per Second每秒生成的 token 数感觉"快不快"
python
import time

def benchmark_model(model, prompt):
    start = time.time()
    
    response = model.generate(prompt, stream=True)
    
    first_token_time = None
    total_tokens = 0
    
    for chunk in response:
        if first_token_time is None:
            first_token_time = time.time()
            ttft = first_token_time - start
        total_tokens += 1
    
    total_time = time.time() - start
    tps = total_tokens / total_time
    
    return {
        "ttft_ms": ttft * 1000,     # 毫秒
        "tps": tps,
        "total_time_s": total_time,
        "total_tokens": total_tokens
    }

# 结果示例
# → TTFT: 350ms, TPS: 45, 生成 200 tokens 耗时 4.4s

9. 质量评估——你的 AI 到底好不好用？ ​

9.1 产品角度的评估维度 ​

维度定义怎么测
准确性回答是否事实正确和标准答案对比
忠实度是否基于提供的资料回答检查是否引用了不存在的信息
有帮助是否解决了用户的问题用户后续是否继续追问
安全性是否产生有害内容安全过滤 + 红队测试
一致性同样问题是否给出不矛盾的答案反复问同样问题

9.2 准确性评估 ​

python
def accuracy_score(answers, ground_truths):
    """计算准确率"""
    correct = 0
    for pred, truth in zip(answers, ground_truths):
        if llm_judge_similarity(pred, truth) > 0.8:
            correct += 1
    return correct / len(answers)

9.3 忠实度评估（RAG 场景） ​

RAG 场景中最大的问题不是"答错了"，而是"答得很好但引用了不存在的资料"。

python
def faithfulness_check(answer, retrieved_docs):
    """检查回答是否基于提供的文档"""
    prompt = f"""
文档内容：{retrieved_docs}

模型回答：{answer}

文档中是否有支持这个回答的证据？
1. 完全支持——回答基于文档
2. 部分支持——部分有依据，部分没有
3. 不支持——回答内容在文档中找不到
    
输出：[1/2/3] + 说明
"""
    return llm_judge(prompt)
忠实度分数含义
90~100%忠实，几乎不瞎编
70~89%偶尔有添油加醋
50~69%经常编造一半内容
<50%几乎都在胡编

9.4 有用性评估 ​

最直接的方式：用户行为指标。

指标含义
用户后续问题数越少越好（一次解答）
用户满意度打分越高越好
问题转化率AI 解决率越高越好
转人工率越低越好

最终判断 AI 质量的不是 benchmark 分数，而是用户是否能用它解决问题。

10. 产品上线检查清单 ​

10.1 质量检查 ​

检查项标准达标？
核心场景准确率>85%✅/❌
幻觉率<5%✅/❌
拒绝回答率<10%（合理范围内）✅/❌
无伤害内容100%✅/❌
一致性测试>90% 场景一致✅/❌

10.2 速度检查 ​

检查项标准达标？
TTFT<500ms✅/❌
TPS>30✅/❌
P95 延迟<3s✅/❌
高峰期稳定不超时✅/❌

10.3 成本检查 ​

检查项标准达标？
单次调用成本<0.01 美元（高频场景）✅/❌
月总成本<预算的 80%✅/❌
用户价值比成本 < 用户付费金额✅/❌

10.4 安全检查 ​

检查项标准达标？
提示注入防护用户不能越狱✅/❌
敏感内容过滤不产生违规内容✅/❌
数据隐私用户数据不泄露✅/❌
内容审核自动 + 人工兜底✅/❌

10.5 最终决策矩阵 ​

所有项都达标 → ✅ 可以上线
质量/安全不达标 → ❌ 不能上线
速度/成本不达标 → ⚠️ 可以小流量测试

质量和安全是红线，速度和成本是优化项。

python
# 简化的智能客服架构

class CustomerServiceBot:
    def __init__(self):
        self.llm = load_model()
        self.knowledge_base = load_vector_db()
        self.clsifier = load_intent_model()
    
    def handle(self, user_input):
        # 1. 意图识别
        intent = self.clsifier.predict(user_input)
        
        # 2. 安全过滤
        if self.is_harmful(user_input):
            return "抱歉，我不能回答这个问题。"
        
        # 3. 知识检索
        docs = self.knowledge_base.search(user_input, top_k=3)
        
        # 4. 生成回答
        response = self.llm.generate(
            system_prompt="基于以下资料回答客服问题",
            context=docs,
            user_message=user_input
        )
        
        # 5. 输出审核
        if self.is_safe(response):
            return response
        else:
            return "转人工客服处理。"

12. AI 产品设计——Copilot ​

12.1 Copilot 和 Chatbot 的区别 ​

维度ChatbotCopilot
角色回答者协作者
交互用户问，AI 答用户做事，AI 辅助
主动性被动主动建议
场景客服、咨询写作、编码、设计
工作流单次对话多步协作

12.2 Copilot 设计原则 ​

1. AI 辅助，不是 AI 替代

好的 Copilot 让用户做决策，AI 做执行。

❌ 差：AI 全自动写一篇文章，用户无法干预
✅ 好：AI 写大纲 → 用户调整 → AI 写段落 → 用户修改

2. 渐进式介入

介入级别例子
被动（默认）用户打字，AI 不打扰
建议用户输入时，AI 自动补全
提示用户卡住时，AI 给出建议
自动化用户确认后，AI 执行

3. 支持撤销

用户：AI 帮我改这段文字为正式风格
AI：（改写后显示）
用户：改得太正式了
AI → 提供"撤销"按钮或者"改成轻松风格"选项

12.3 典型 Copilot 架构 ​

python
# 简化的写作 Copilot
class WritingCopilot:
    def __init__(self):
        self.llm = load_model()
        self.suggestion_cache = {}
    
    def on_type(self, current_text, cursor_position):
        """用户打字时触发"""
        
        # 看是否需要建议
        if self.should_suggest(current_text):
            suggestion = self.llm.generate(
                f"用户正在写：{current_text}\n"
                f"光标在位置：{cursor_position}\n"
                f"请给出下一句建议（5~20 字）"
            )
            return {"suggestion": suggestion, "type": "autocomplete"}
        
        return None
    
    def on_command(self, command, text):
        """用户主动请求 AI 操作"""
        
        if command == "rewrite":
            result = self.llm.generate(f"改写以下文字为更正式风格：{text}")
            return {"result": result, "undo_available": True}
        
        if command == "summarize":
            result = self.llm.generate(f"总结这段文字：{text}")
            return {"result": result, "format": "bullet_points"}
        
        if command == "translate":
            result = self.llm.generate(f"翻译成英文：{text}")
            return {"result": result, "inline": True}

14. AI 产品思维——什么时候不用 AI ​

14.1 AI 不是万能药 ​

这是本课最重要的一节。AI 很强大，但不是所有问题都适合用 AI 解决。

14.2 适合用 AI 的 ​

场景为什么适合
需要理解自然语言搜索、问答、翻译
需要生成内容写作、代码、设计
需要处理大量文本分类、提取、总结
需要模糊匹配不是精确匹配，是"差不多"
需要个性化每个人的回答不一样

14.3 不适合用 AI 的 ​

场景为什么不用更好方案
精确计算AI 不能保证 100% 准确用普通代码
固定流程用 AI 反而慢用 if-else
高可靠性要求AI 会幻觉用确定性系统
同输入同输出AI 每次结果不同用缓存/规则
简单分类杀鸡用牛刀用关键词匹配

14.4 决策框架 ​

遇到问题 →
├── 能否用规则/公式精确解决？
│   ├── 是 → 不用 AI，写代码
│   └── 否 →
│       ├── 需要理解自然语言？
│       │   ├── 是 → 考虑 AI
│       │   └── 否 →
│       │       ├── 需要创造性？
│       │       │   ├── 是 → 考虑 AI
│       │       │   └── 否 → 考虑规则系统
│       └── 容错率高吗？
│           ├── 高 → 可以 AI
│           └── 低 → 不要 AI

14.5 产品经理的灵魂拷问 ​

上线前问自己 5 个问题：

  1. 不用 AI 能做到同样效果吗？ → 能的话就别用 AI
  2. 用户真的需要这个 AI 功能吗？ → 还是你觉得"酷"才做？
  3. 回答错了会怎样？ → 如果后果严重，先加防护
  4. 这个功能赚钱吗？ → 成本 - 收益算清楚
  5. 数据隐私呢？ → 用户数据你敢给第三方 API 吗？

最贵的 AI 功能 = 做了没人用的 AI 功能。

15. 常见误区 ​

误区真相
"Benchmark 分数高就等于产品好"学术分数和实际体验差很远
"人类评估太贵了，只看自动评估"自动评估和人类偏好的相关性只有 60~80%
"GPT-4 是最好的"在小任务上 GPT-4o-mini 可能更合适
"成本不重要，好用就行"成本×调用量 = 巨额账单
"用户喜欢最快的响应"用户更喜欢"正确但不那么快的"
"AI 能解决所有问题"AI 不是万能药，很多问题用规则解决更好
"上线后就不用管评估了"评估是持续过程，产品变了模型也要重新评估

16. 本课总结 ​

核心要点 ​

  1. 评估：用公开基准（MMLU/GSM8K/HumanEval）做初筛，用业务评估集做最终判断
  2. 人工+自动：人工评估是黄金标准，LLM-as-Judge 是性价比方案，组合使用
  3. 成本核算：输入×价格 + 输出×价格 = 单次成本，然后×调用量 = 月成本
  4. 速度指标：TTFT（首字速度）影响第一印象，TPS（生成速度）影响体验
  5. 上线检查：质量 > 安全 > 速度 > 成本（但都要过线）
  6. 产品设计：Chatbot 看 UX 引导，Copilot 看辅助协作，SaaS 看无缝集成
  7. AI 思维：知道什么时候不用 AI，比知道怎么用 AI，更重要

一句话记住 ​

AI 产品经理的核心能力不是"怎么用 AI"，而是"什么时候用 AI、怎么判断 AI 好不好、上线后怎么优化"。

17. 心智模型 ​

评估心智模型 ​

评估类似看病：
  面试（Benchmark）→ 初筛，看看基本素质
  体检（业务评估集）→ 针对你的场景细致检查
  定期复查（持续评估）→ 确保一直健康

成本心智模型 ​

每 1 元成本 = 用户使用价值 > 1 元
如果用户免费使用，成本就是纯支出
所以要么降低到接近 0，要么让用户愿意付费

选择心智模型 ​

遇到问题 →
├── 可以用规则 → 别用 AI
├── 可以用小模型 → 别用大模型
├── 可以用本地 → 别用 API
└── 必须用大模型 API → 控制成本和速度
